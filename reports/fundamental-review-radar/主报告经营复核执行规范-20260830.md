# 主报告经营复核执行规范

> 版本：v1.1 · 生效日：2026-08-30 · 数据截止：2026-08-30 · 状态：**后续复核的唯一执行规范**
>
> 适用范围：AI Berkshire A 股主报告的经营、财务与事件复核。本规范是研究流程，不构成投资建议。

## 1. 目的与边界

这套流程只回答一个问题：**主报告中已人工锁定的条件、改善信号和风险红线，是否有主报告之后的可靠证据支持？**

它不做以下事情：

- 不改写主报告结论、价格带、红线、阈值或条件关系；
- 不以 Checklist、技术面、情绪面、旧 `manual_execution_review` 或模型共识替代证据；
- 不因价格变化触发基本面模型复核；价格仍由既有人工价格分区处理；
- 不把“公司收入增长”泛化为“订单、回款、海外项目利润率已验证”。

人工锁定规则是唯一当前权威。日常模型、ZCode、DeepSeek 和 Codex 的角色均是**证据核验员**：可以提出缺口和候选差异，不能自动改规则。

日常复核可接收看板行情快照作为只读 `price_context`（价格、时间、来源与新鲜度），用于让结果有当时的行情背景；它**不是经营证据**，不得用于任何规则的 `met/not_met`，也不得触发模型复跑、修改价格带或改变价格分区。

日常 OpenCode 代理 `deploy/opencode/agent/fundamental-review-daily.md` 必须在每次任务开始前读取本文件；未来变更须提高本文件版本号，并由人工确认后再应用到代理或工具。

## 2. 本轮 93 股复核暴露的规则

本次在 93 只 A 股上完成独立结果文件后，状态分布为：

| 状态 | 数量 | 含义 |
|---|---:|---|
| `warning` | 74 | 已取得当前证据，但至少一项锁定条件、连续期或事件仍未完整核验 |
| `data_insufficient` | 14 | 未形成足够的主报告后双源证据，不能判断 |
| `attention` | 2 | 已出现需要人工关注的经营边际变化 |
| `redline` | 1 | 有证据表明锁定的重审红线触发，需人工重审主报告 |
| `waiting_official_disclosure` | 1 | 等待正式披露，不能用旧报告填补 |
| `rule_stale` | 1 | 主报告正文变更，原锁定规则停止参与当前判断 |

这意味着“警告”并不等于经营恶化；大量公司是**财报已经披露，但报告要求的订单、客户认证、项目回款、分部利润、海外政策或连续季度条件尚未披露**。正确动作是保留缺口，而不是把它们写成已通过。

## 3. 规则版本与失效

### 3.1 锁定方式

每只股票的有效规则必须绑定：

- 主报告路径；
- 规范化 SHA-256（UTF-8、去 BOM、CRLF/CR 统一为 LF）；
- 人工锁定时间；
- 规则原文、来源字段、行号和条件关系。

规范化哈希避免 Windows 与 macOS 仅因换行符不同而产生假失效。

### 3.2 主报告修改后的处理

| 情况 | 处理 |
|---|---|
| 哈希一致 | 规则为 `active`，可继续复核 |
| 哈希不一致 | 规则立即为 `stale`，旧规则只读留档，不参与当前红线/改善结论 |
| 人工确认新版主报告 | 重新抽取并人工确认规则后，生成新规则版本；旧结果保留历史链路 |

模型只能给出“可能有差异的段落和原文定位”，**不得**自动把旧规则迁移到新版报告。平高电气（600312.SH）本轮即属于 `rule_stale`，是这条规则的实际案例。

## 4. 原子规则的写法

一条规则只表达一个可审计命题，不能把“买入前提、改善条件、卖出红线”混在一条大段文字里。推荐字段：

```json
{
  "rule_id": "human_locked.redline.redline.1",
  "group": "redline",
  "polarity": "negative",
  "condition": "连续两个季度毛利率低于30%",
  "relation": "all_of",
  "metrics": ["毛利率"],
  "operator": "<",
  "threshold": "30%",
  "periods": ["连续两个季度"],
  "schedule_type": "filing",
  "evidence_requirement": ["current_value", "comparison", "official_source"],
  "source_lines": [{"line_start": 120, "line_end": 124}]
}
```

固定分组如下：

| `group` | `polarity` | 含义 |
|---|---|---|
| `entry` | `positive` | 买入前提；价格部分交给价格分区 |
| `holder` | `monitoring` | 持有期需持续跟踪的事实 |
| `improvement` | `positive` | 经营改善或升级条件 |
| `redline` | `negative` | 失效、重审或风险红线 |

价格条件即使在旧数据中被放在 `risk` 字段，也必须留在价格层，不能被日常经营复核误报为负向红线。

## 5. 证据纪律

### 5.1 来源优先级

1. 主报告之后的本地最新材料：tracker、论文更新、已人工保存的公司纪要或正式资料；
2. 公司公告、巨潮、交易所、公司投资者关系页面和正式财报；
3. 可交叉验证的结构化公开数据；
4. 找不到时写 `data_insufficient`，并列出缺什么。

主报告只说明“规则是什么”和“历史基线是什么”，**不能**作为当前事实证据。搜索结果摘要只可用来发现来源，不能作为结论证据。

### 5.2 A 股财务双源核验

对于收入、归母净利润、扣非净利润和经营现金流：

- 来源一：东方财富 F10 结构化财务数据；
- 来源二：巨潮/交易所正式财报；
- 误差 `<=1%`：可标记一致，以正式财报为事实锚；
- 误差 `1%–5%`：标记口径差异并解释；
- 误差 `>5%`：不得使用，先回到原始财报核查。

正式财报有时以“千元”列示、结构化数据以“元”列示。允许统一单位后的舍入差，但必须记录原始单位和比较方式，不能把 PDF 文本提取失败伪装成 0 差异。

### 5.3 不可替代的证据

下列内容不能由收入或利润增长代替：

- 海外/虚拟电厂/新产品订单；
- 回款和应收质量；
- 项目级利润率；
- 客户认证、良率和产线爬坡；
- 政策、监管、关税、重大安全事故；
- 商誉减值、治理或管理层事件。

这些事项须有相应的公司公告、正式财报分部披露、官方事件文件或明确的“未披露”结论。

### 5.4 PDF 取证方式

不得把整份 PDF 的开头机械截断后交给模型。调用程序须先下载完整官方 PDF，再按**当前锁定规则的指标和事件关键词**定位相关页、表格附近段落和相邻上下文，保留页码与行号。模型上下文可限制为“相关证据预算”，但不能以“每份 PDF 前 N 字”替代定位。

官方 PDF 数量按当前有效规则覆盖范围选择：财报、订单、项目、政策或监管事项都可入选；不得固定只读取最先返回的三份。运行时可以设置网络与解析的安全上限，但必须在结果中记录选取文件、页码和选取方法。

### 5.5 事件类未披露

事件规则除 `truth_state` 外，必须记录 `disclosure_state`：

| `disclosure_state` | 含义与处理 |
|---|---|
| `disclosed` | 有主报告之后的正式官方披露与原文定位；才可判 `met` 或 `not_met` |
| `not_disclosed` | 已检索规定范围的官方渠道，未见该事项披露；`truth_state` 必须为 `unknown`，不等于事件未发生 |
| `not_due` | 规则本身记录了明确的未来事件日期，且当前日期尚未到达；没有明确日期不得使用 |
| `search_incomplete` | 没有完成规定官方渠道检索或来源不可访问；`truth_state` 为 `unknown` |

订单、客户、项目利润率、海外回款等未公开细项，正确结果通常是 `not_disclosed` 或 `search_incomplete`，并列出下一项需要的公告/财报，而不是推定“没有”或“已验证”。

## 6. 判定规则

每个原子规则仅使用四种事实状态：

| `truth_state` | 含义 |
|---|---|
| `met` | 当前证据完整支持条件已满足；复合条件必须全部满足 |
| `not_met` | 当前证据完整支持条件未满足 |
| `unknown` | 缺当前值、对比期、官方来源或事件确认，不能推断 |
| `not_due` | 价格条件或尚未到披露/事件窗口，不进入本轮经营判断 |

复合条件使用 `all_of` 时，缺任一组成部分即为 `unknown`，不得写成 `met`。`any_of` 仅在至少一个分支有完整证据时才能给出肯定结论。事件规则只有 `disclosure_state=disclosed` 且有官方原文时才能使用 `met/not_met`。

再映射为复核影响：

| 规则类型 | `met` | `not_met` | `unknown` |
|---|---|---|---|
| 改善条件 | `positive` | `neutral` | `warning` 或 `neutral`（按是否到期） |
| 持有监控 | `neutral` | `warning` | `warning` |
| 风险红线 | `redline` | `neutral` | `neutral`，同时保留数据缺口 |

“触发”只能用于真正的负向红线；正向改善条件满足只能叫“改善”，不能叫“红线触发”。

## 7. 单股输出、保存与复跑

每只股票写入独立 JSON：`local/fundamental-review-codex-manual/<ticker>.json`。至少包含：

- 主报告路径、规范化哈希和规则状态；
- 复核人及 `models_used`；
- 证据标题、日期、URL、哈希、页码/段落和事实；
- 双源比较、误差及单位说明；
- 每条规则的 `truth_state`、影响和理由；
- 汇总状态、红线、待核验项与下一份所需证据。

写入一律使用：临时文件 → `fsync` → 原子替换。任一股票失败只影响自身，绝不把 93 股汇总文件作为人工写入源。

复跑触发条件：

1. 主报告哈希变化；
2. 新本地材料、正式财报或公告出现；
3. 规则的财报窗口到期；
4. 明确事件条件发生。

价格变动只刷新价格分区，不触发基本面复核。

## 8. 日常模型与人工复核的分工

| 层级 | 可以做什么 | 不能做什么 |
|---|---|---|
| 日常模型 | 按固定规则发现当前官方证据、列事实和缺口、给 JSON 候选结果 | 改阈值、把主报告基线当当前事实、给交易指令 |
| ZCode/其他模型审计 | 发现规则遗漏、语义歧义和原文定位 | 覆盖人工锁定规则 |
| 人工/Codex | 确认新主报告后重锁规则；裁决红线和语义冲突 | 以无来源的常识补造条件 |

日常模型的输出必须先通过本规范的证据完整性检查；没有当前官方证据时，正确答案就是 `data_insufficient`，不是凭旧报告给“已验证”。

## 9. 看板展示边界

主表只显示紧凑状态徽标：`红线`、`需关注`、`数据不足`、`等待披露`、`规则失效`。详情页才显示规则原文、证据、差异、缺口和页码。

复核状态不得覆盖：

- 当前可执行分区；
- 最近行情参考分区；
- 人工价格分区；
- 主报告原文判断。

它是“经营证据是否支持主报告”的独立层，而不是自动交易信号。

## 10. 每次运行前的最小清单

1. 核对主报告规范化哈希是否仍为 `active`；
2. 只收集主报告之后的本地或官方证据；
3. 财务四项做东方财富 + 正式财报双源比较；
4. 对订单、回款、分部利润、政策等分别找对应证据；
5. 复合条件缺项即 `unknown`；
6. 单股原子写入；
7. 校验 93 只覆盖、无模型越权、无 >1% 未解释差异；
8. 只有在用户确认后，才将汇总结果构建到看板或部署。

## 11. 规范演进闭环

规范不是永久不变的，但也不能由一次模型输出直接覆盖。每轮复核按以下闭环运行：

1. 单股结果除规则事实外，可记录 `protocol_findings`：证据缺口模式、来源访问问题、单位/报告期映射、规则语义歧义或输出结构缺口；
2. 批量结束后运行 `tools/main_report_review.py --write-protocol-findings`，在结果目录生成 `protocol-findings-current.json`；它按问题类别汇总股票、原始证据和待讨论问题；
3. 人工/Codex 审阅汇总，判断问题是单股资料缺失、数据源临时异常，还是应修改全局规范；
4. 只有确认属于全局流程问题时，统一更新本文件、提升版本号，并同步更新日常代理与必要的校验代码；
5. 规范更新不自动改变既有主报告规则。若修改影响规则解释或证据门槛，旧复核结果应保留版本和输入指纹，并按新规范重新复核受影响股票。

`protocol-findings-current.json` 是候选审阅队列，不是自动生效的规范补丁。这样既能从后续问题持续学习，又不会让单个模型错误或单只股票的特殊情况污染全部 93 股。
